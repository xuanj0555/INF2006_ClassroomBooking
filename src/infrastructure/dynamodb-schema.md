# DynamoDB Data Model

## Overview

Roomly stores live application data in four DynamoDB tables in
us-east-1. Historical reservation analytics are stored separately
in S3 and are not part of these live tables.

## 1. Rooms

Purpose: Stores the rooms available in Roomly.

Partition key: `room_id` — String  
Sort key: None

| Attribute | Type | Purpose |
|---|---|---|
| room_id | String | Unique room identifier, such as R001 |
| name | String | Display name |
| capacity | Number | Maximum number of participants |
| location | String | Room location |
| is_active | Boolean | Whether the room accepts new bookings |

New room identifiers are generated by the backend.
Amenities are not part of the current room data model.

## 2. RoomlyUsers

Purpose: Stores application users and their permissions.

Partition key: `user_id` — String  
Sort key: None

| Attribute | Type | Purpose |
|---|---|---|
| user_id | String | Application identifier, such as U001 |
| name | String | Display name |
| role | String | Application role, such as student or faculty |
| is_active | Boolean | Whether the account may use the application |
| is_admin | Boolean | Whether the user has administrator permissions |

Additional identity-mapping attributes connect the user record
to the Cognito issuer and subject identifier. Record their exact
attribute names from the deployed implementation.

Passwords are managed by Cognito and are not stored in this table.
Faculty status alone does not grant administrator permission.

## 3. RoomlyBookings

Purpose: Stores booking details and lifecycle information.

Partition key: `booking_id` — String  
Sort key: None

| Attribute | Type | Purpose |
|---|---|---|
| booking_id | String | Unique booking reference |
| room_id | String | Reserved room |
| organiser_id | String | User who created the booking |
| participant_ids | List of Strings | Users included in the booking |
| start_time | String | Start timestamp with timezone offset |
| end_time | String | End timestamp with timezone offset |
| status | String | Booking status, such as confirmed or cancelled |
| created_at | String | Creation timestamp |
| cancelled_at | String | Cancellation timestamp, when applicable |
| attendance_outcome | String | Recorded attendance state |
| check_in_time | String | Check-in timestamp, when applicable |
| fingerprint | String | Identifies an equivalent booking submission |

Optional attributes are present only when applicable.
Cancelled booking records are retained for history.

## 4. RoomlyReservations

Purpose: Prevents conflicting room and participant reservations
and stores coordination records.

Partition key: `resource_id` — String  
Sort key: `slot_start` — String

| Attribute | Type | Purpose |
|---|---|---|
| resource_id | String | Identifies a room, user or system record |
| slot_start | String | Identifies the reserved slot or system metadata |
| booking_id | String | Booking associated with a reservation |
| revision | Number | Coordinates concurrent application changes |
| last_room_number | Number | Tracks automatic room-number generation |

Example reservation records:

- `ROOM#R001` with a slot timestamp reserves room R001.
- `USER#U001` with the same slot timestamp reserves user U001.

System records:

- `SYSTEM#BOOKING_STATE` / `META` stores the mutation revision.
- `SYSTEM#ROOM_SEQUENCE` / `META` stores the room-number sequence.

The attributes vary by record type. A room reservation does not
need the attributes used by a system record.

## Booking creation and cancellation

Booking creation uses a DynamoDB transaction to write the booking,
room reservation, participant reservations and coordination update
together. Conditional checks prevent existing reservation records
from being overwritten.

Cancellation uses a transaction to mark the booking as cancelled,
remove its room and participant reservation records, and update
the coordination record. This releases the slot while preserving
the cancelled booking history.

If a transaction fails, its changes are not partially committed.

## Relationships

Bookings reference rooms through `room_id` and users through
`organiser_id` and `participant_ids`. Reservation records reference
bookings through `booking_id`.

DynamoDB does not enforce relational foreign keys. The backend
validates these relationships and applies booking rules.
